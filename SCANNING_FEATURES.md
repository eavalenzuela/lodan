# lodan — New Scanning Features (Round 2)

Every feature below stays inside lodan's hard contract: strictly detection-only, no credentials ever sent, no auth/login/exploitation/evasion/DoS. The most active behavior any of these introduces is a bounded, standards-shaped handshake that stops at or before the server's authentication challenge — most are pure post-processing of bytes existing probes already collected. The theme is depth: squeezing more identity, crypto posture, and exposure signal out of packets the target already volunteers, and folding each new signal into the pivot and diff engines that make lodan lodan.

One cross-cutting design note: non-CVE posture verdicts (weak crypto, TLS hygiene, unauth exposure) all land in the single `findings` table introduced in feature 10 rather than being smuggled into `vulns` as pseudo-CVEs — `vulns` has no FTS index and isn't diffed, whereas `findings` is severity-scored, FTS-backed, and diffable by construction. Genuine CVE identifiers (e.g. ROCA's CVE-2017-15361, version-matched advisories) still go to `vulns`.

### 1. Passive TCP/IP stack fingerprinting from the discovery SYN-ACK
**What:** Fingerprint the OS/stack from the SYN-ACK lodan already receives during discovery — initial-TTL guess, TCP window, MSS, window-scale, option order, SACK/timestamps, DF bit, IP-ID behavior — into a stable `stack_sig` + `os_family`, and derive two orthogonal secondary signals from the same bytes: **hop-count** (initial_ttl − observed) and **TCP-timestamp clock-skew** for cross-IP physical-host de-duplication.
**Why it matters:** The SYN-ACK is the single richest passive OS signal on the wire and lodan currently discards everything below the application layer. TTL/window profiling gives an OS estimate independent of banners; hop-count feeds a topology dimension the port/service diff can't see; clock-skew clusters multiple IPs onto one physical machine — a physical-identity pivot complementing the logical ones.
**How it fits lodan:** `discovery/scapy_backend.py::_classify` already holds the full `rcv[IP]`/`rcv[TCP]` packet but extracts only src/dport — it is the one backend with the raw SYN-ACK, so it is the full-signal path. Extend `DiscoveryResult` (`discovery/base.py`) with nullable stack fields, add a pure fingerprint module (mirrors `enrich/tech_signatures.py`), and add `stack_sig`/`os_family`/`hop_count` columns + index to `services`/`hosts` in `store/schema.sql`, plus a `stack_sig` key in `query.py`'s `_VALID_KEYS` so it becomes a pivot like `ja4s`. The masscan backend currently parses masscan's *list* output (`open <proto> <port> <ip> <ts>`), which carries no TTL; TTL can be surfaced only by switching `build_argv` to masscan's JSON output and adding a JSON line parser (a scoped follow-on, partial signal). The naabu connect-scan backend exposes no L3/L4 fields and degrades gracefully to null. A `path_changed` diff kind and a clock-skew-cluster pivot slot into `diff/scanner.py` (extend both the `KINDS` tuple and the `DiffCounts` dataclass) and `store/query.py`.
**Detection-only:** Reads fields off the SYN-ACK the host already sent in reply to the discovery SYN — zero additional packets, no payload, no traceroute, no injected timing probes.

### 2. OS, distro & device-type inference via multi-signal fusion
**What:** Two layers. First, mine the version strings probes already parse (OpenSSH comment `Ubuntu-4ubuntu0.5` → Ubuntu 20.04, `Microsoft-IIS/10.0` → Windows Server, Exim/vsFTPd build hints) into a structured `os_guess`. Then a weighted rule engine fuses the whole per-host feature vector — open-port set, `os_family`/`stack_sig` from feature 1, banners, favicon labels, JA3S/JA4S, SMB/RDP/MQTT/Docker/k8s presence — into a `device_type` verdict: server, router/firewall, printer, IP camera/IoT, NAS, hypervisor, container host.
**Why it matters:** "What OS/what box is this" is the canonical recon question. lodan already collects every input but never combines them; banner-OS and the passive stack fingerprint give two independent OS estimates that corroborate or conflict, and device-class flips (server→appliance) become meaningful `changed` diffs.
**How it fits lodan:** New `enrich/device.py` pass structured like the CVE/tech matchers, plus a banner-regex signature table modeled on `enrich/tech_signatures.py`. Reads `SSHBanner.comment` (the `comment` field already parsed by `ssh.py`), HTTP `Server`/`X-Powered-By`, SMTP/FTP greetings, and the assembled service rows; writes `os_guess` on `services` and `device_type` + confidence on `hosts`.
**Detection-only:** Pure inference over already-stored banner text and fingerprints; issues no traffic.

### 3. NAT / load-balancer & backend-count detection
**What:** Flag a single IP as fronting multiple backend machines when its per-port fingerprints disagree in ways one host cannot produce — two distinct SSH host keys, mutually exclusive OS-stack signatures (Linux on :443, Windows on :3389), disjoint JA3S/JA4S clusters, or clashing cert issuers — and emit a `min_backend_count`.
**Why it matters:** Reframes per-service fingerprints into the host-topology answer operators actually want ("this /24 is really 4 boxes behind one VIP"). It reuses signals already stored and feeds lodan's headline diff: a new `topology_change` kind fires when backend count shifts scan-to-scan.
**How it fits lodan:** Pure post-scan correlation over `services` (new pass in `scan.py`/`store/query.py`). Group by `(scan_id, ip)`, compare the fingerprint set (`ssh_hostkey`, `stack_sig`/`os_family` from feature 1, `ja3s`/`ja4s`, `cert_fingerprint`) across ports, set host-level `nat_suspected`/`min_backend_count`, and register `topology_change` in `diff/scanner.py` (`KINDS` + `DiffCounts`).
**Detection-only:** Read-only correlation over the SQLite store; adds no traffic whatsoever.

### 4. TLS posture deep-dive: full chain, acceptance matrix, JARM & hygiene findings
**What:** Three complementary TLS upgrades. **(a)** Parse and store *every* cert in the chain, not just the leaf — subject/issuer/serial, key type+bits, sig algo, validity, CA flag, path position — with hygiene flags (expired, expires-soon, self-signed, incomplete/out-of-order chain, RSA<2048, SHA1/MD5, SAN mismatch). **(b)** Enumerate accepted protocols/ciphers via a small parameterized ClientHello matrix (is TLS 1.0 still on? does it accept 3DES/RC4/NULL? forward secrecy?). **(c)** Compute the 62-char **JARM** active server fingerprint from JARM's 10 standardized hellos.
**Why it matters:** `parse_stream` already calls `extract_cert_chain` but keeps only `chain[0]`, and `build_client_hello()` takes no arguments and hardcodes a single TLS 1.2 hello — so lodan can't answer the core posture questions (expired cert on a prod port, legacy TLS enabled, weak cipher accepted) despite handshaking every time. JARM adds an active configuration-clustering pivot that a single ServerHello can't produce.
**How it fits lodan:** Generalize `build_client_hello()` into a parameterized builder and thread the chosen hello through `fetch()` (the `ClientHelloBytes`/`_CIPHERS`/`_SUPPORTED_GROUPS` machinery already exists); reuse `parse_server_hello`. Add a `chain_certs` table + a `jarm` column/index (mirroring `services_ja4s`) with a `jarm:` key in `query.py`. Store each chain cert's DER so key material is available offline to feature 5. Route hygiene/weak-crypto verdicts (`TLS-EXPIRED`, `TLS-LEGACY-1.0`, `TLS-WEAK-CIPHER`) into the `findings` table from feature 10 so they inherit severity, FTS, and `new_exposure`/`gone_exposure` diffing. Extend the `cert_fingerprint` pivot to any chain depth for CA-reuse clustering.
**Detection-only:** Certs arrive unsolicited in the existing ServerHello/Certificate flight; each acceptance/JARM connection is a ClientHello → read ServerHello → close, bounded to a fixed small count — identical in intrusiveness to the current single-hello probe. No handshake completion, no appdata, no creds.

### 5. SSH KEXINIT audit + cross-protocol key-strength scoring
**What:** Capture the server's `SSH_MSG_KEXINIT` (sent immediately after ident exchange, pre-auth) and enumerate offered KEX/cipher/MAC/host-key algorithms, flagging deprecated ones (`diffie-hellman-group1-sha1`, `ssh-rsa`/`ssh-dss` SHA1, CBC, arcfour/3des, hmac-md5). Then unify weak-key detection across *all* captured public keys — TLS leaf+chain and SSH host keys: RSA<2048, DSA/1024-bit, SHA1/MD5 signatures, deprecated curves, and an offline **ROCA** (CVE-2017-15361) modulus test.
**Why it matters:** The SSH probe records banner + host-key fingerprint but never the negotiable algorithm set, which is exactly where deprecated crypto hides (modern banner, `hmac-md5` still offered). And lodan captures key material but never judges its strength — a 1024-bit cert or ROCA-vulnerable key is invisible today. Both are strong diff targets when hardening removes a weak algo/key.
**How it fits lodan:** In `ssh.py`, after the existing ident read, send lodan's own ident line and read the unsolicited `SSH_MSG_KEXINIT` (RFC 4253 §7.1 name-lists) with a small hand-rolled binary reader in the same spirit as the hand-rolled TLS parser — this stops before any Diffie-Hellman exchange. Extend `_fingerprint_keys` to also persist each host key's public parameters (RSA modulus/bits) into `ProbeResult.raw`, since it currently keeps only the sha256 fingerprint and discards the modulus ROCA needs. Add `enrich/keyposture.py` (structured like `cve.py`) consuming those stored moduli plus the DER chain certs captured by feature 4. Non-CVE weak-algo/weak-key verdicts go to the `findings` table (feature 10); the ROCA hit is a real CVE and goes to `vulns` (`source='keyposture'`, `cve='CVE-2017-15361'`, with confidence scoring).
**Detection-only:** Ident exchange + reading the server's volunteered KEXINIT requires no auth and stops before key exchange; ROCA and the size/signature checks are pure offline math on a public modulus.

### 6. UDP probe transport + high-value datagram service fleet
**What:** Unlock the UDP probe path discovery already populates, then ship a fleet of read-only datagram probes: **SNMPv2c** `sysDescr.0`/`sysObjectID.0` (device model/OS/firmware + IANA vendor), **NTP** mode-6 readvar + monlist-enabled detection with an amplification-factor field, **memcached** `stats`, **SSDP/UPnP** M-SEARCH (`SERVER` string) and **mDNS** DNS-SD service-type enumeration, **NetBIOS-NS** NBSTAT (computer/workgroup name + adapter MAC → OUI vendor), and **IKE/IPsec** transform + Vendor-ID gateway fingerprinting.
**Why it matters:** SNMP/UDP-161 is one of the highest-value recon leaks on owned ranges (full device inventory + OS/firmware straight into CPE matching) and lodan discovers it but is structurally blind to it. NTP/memcached quantify **amplification-reflector exposure** as a first-class, queryable property. SSDP/mDNS/NetBIOS/IKE reach IoT, embedded, Windows/Samba, and VPN-gateway classes that TCP banner/TLS probes never touch, and MAC-OUI + NetBIOS name are stable cross-scan identity pivots.
**How it fits lodan:** `probes/dispatch.py::pick_probes` currently returns `[]` for `proto != 'tcp'`; give probes a `proto` (default `tcp`) and match on `(port, proto)` so `runner.py` — which already threads `proto` through `_run_one` — dispatches UDP. Add a `UdpProbe` helper over `loop.create_datagram_endpoint` mirroring the `mqtt.py`/`redis.py` fetch shape (single send, bounded read, timeout). Each probe emits `ProbeResult` feeding `enrich/cve.py` CPE matching and `services_fts`; add `netbios_name`/`mac_oui`/`ike_vendor_id` pivot columns + indexes and an `amp:` numeric key (registered in both `_VALID_KEYS` and `_INT_KEYS` in `store/query.py`). OUI→vendor reuses the offline-table pattern of `enrich/ip2location_data.py`.
**Detection-only:** One well-known unauthenticated read per service — no PSK/community guessing, no wordlists, no SET/write, no source spoofing, no monlist harvest loop, never a completed tunnel. **Boundary note on SNMP:** SNMPv2c has no bannerable handshake, so the "is SNMP exposed" check necessarily carries a community string. lodan sends *only* the single RFC-default `public` community, never a second value and never a guessing loop, and treats a response as an **exposure finding** (default-community SNMP is itself the misconfiguration to report) rather than a foothold to pivot from — the SNMP/NTP analogue of the repo's Redis-INFO / empty-MQTT-CONNECT reads. Because `public` is a default access token rather than a bannergrab, this one probe ships behind an explicit operator opt-in.

### 7. TCP pre-auth handshake probe fleet
**What:** A batch of high-traffic TCP services that leak version and auth-mechanism data before authentication: **MySQL** initial handshake (version, thread id, auth plugin, capability flags — zero bytes sent), **PostgreSQL** SSLRequest + AuthenticationRequest tag (trust/md5/scram → passwordless-`trust` exposure), **VNC** RFC 6143 ProtocolVersion + offered security types (`None` in the offered list = open VNC), **AMQP** Connection.Start (product/version/platform + SASL mechanisms), and **LDAP** anonymous rootDSE (naming contexts, supported controls, vendor).
**Why it matters:** These are the highest-value TCP services lodan doesn't yet fingerprint, and several expose an outright unauthenticated foothold (open VNC, Postgres `trust`) that is a first-order finding, not just inventory. All version strings flow into the CPE/CVE matcher.
**How it fits lodan:** Five TCP probes on the existing dispatch, each mirroring the `mqtt.py`/`redis.py` fetch-parse shape. MySQL/VNC/AMQP are server-first reads; Postgres sends the 8-byte SSLRequest + a minimal StartupMessage and reads only the auth-method tag; LDAP sends an unbound base-scope rootDSE search. The `None`/`trust` exposures are emitted to the `findings` table (feature 10) so the diff engine reports them via `new_exposure`; version strings feed `services_fts`.
**Detection-only:** Every probe stops at or before the server's authentication challenge. Postgres observes the auth-method tag without ever sending a password; the StartupMessage/LDAP rootDSE carry only the protocol-mandatory routing fields, never a secret, password, or bind DN. No credential is ever transmitted.

### 8. Version-range CVE matching with structured-version CPEs
**What:** Two precision fixes to the vuln matcher. **(a)** Build CPEs from the structured version fields probes already store in `services.raw` — Redis `redis_version`, Docker `Version`, MongoDB `version`, k8s `gitVersion`, Elasticsearch, HTTP `X-Powered-By`/`generator` — not just banner text. **(b)** Ingest NVD's `versionStartIncluding`/`versionEndExcluding` bounds and evaluate the parsed version against them instead of the current exact-prefix `LIKE` match.
**Why it matters:** Whole protocol families get zero CVE coverage today because `_banner_from_raw` only flattens `banner`/`title`/`server` plus `parsed.software`, and the six recognizer regexes only catch web-server/SSH banners. Range-expressed CVEs (the majority of modern NVD entries, e.g. "httpd up to 2.4.54") are stored by `parse_record()` as bare `:*:*` criteria — it currently drops the `versionStartIncluding`/`versionEndExcluding` fields entirely — so they can *never* match a prefix ending in a concrete version. This is the single biggest precision gap in lodan's vuln output: both missed advisories and, from range evaluation, suppressed false positives.
**How it fits lodan:** Add a `raw_to_cpes()` recognizer set in `enrich/cve.py` keyed off the per-probe JSON in `raw` (higher confidence 0.9, authoritative fields). Add `version_start`/`version_end`/inclusivity columns to `cve_cpe` (`cve_schema.sql`), populate them in `parse_record()`, and rewrite `match_cpes()` to match on the `vendor:product` prefix then compare `CPEGuess.version` against the bounds with a small semver/tuple comparator (handling OpenSSH `8.2p1`, already parsed by `ssh.py`). Needs a shared-DB schema bump — coordinate with the planned DB-versioning work rather than duplicating it.
**Detection-only:** Entirely offline evaluation over the cached NVD snapshot and already-collected versions; touches no target.

### 9. Rising-risk analysis: EOL-software exposure + exploit-aware scoring with a posture diff
**What:** Ingest three offline datasets — an **endoflife.date**-style EOL dataset, FIRST **EPSS** (exploit probability + percentile), and **CISA KEV** (confirmed exploited-in-the-wild, with date-added/ransomware flag) — join them onto detected software and every `vulns` row, and add a `risk_increased` diff kind for services that became newly-KEV, crossed their EOL date, or gained a higher-severity match while unchanged on the wire.
**Why it matters:** lodan's diff engine is topology-only today — it has no notion of a host getting *more dangerous* while static. EOL detection is a genuine wire-derived exposure signal that CVE matching misses by design (an out-of-support OpenSSH/Apache/Redis/k8s branch is a standing exposure with no specific CVE), and the newly-KEV / newly-EOL transitions turn the killer diff into a security-posture delta. EPSS/KEV are the standard offline inputs for ranking the resulting list.
**How it fits lodan:** Mirror the `cve_data.py` ingestion/`update()` pattern for `eol`, `epss`, and `kev` tables in the shared `~/.lodan/data` DB via offline downloaders. Derive an EOL verdict from the `os_guess`/version fields (features 2/8) and a `priority` from EPSS/KEV during `enrich_cves()`; expose them as sortable/filterable keys in the query DSL; extend `diff/scanner.py` (`KINDS` + `DiffCounts`) with `risk_increased` carrying the delta detail.
**Detection-only:** Static scored datasets fetched out-of-band exactly like the NVD snapshot, aggregated and diffed locally; no probe traffic of any kind.

### 10. First-class exposure findings table + `new_exposure` diff
**What:** Promote unauth-service and web-misconfig signals that today live only in banner/body text into a structured, severity-scored, diffable findings category: Redis with no NOAUTH, reachable Docker `/version`, unauthenticated MongoDB/Elasticsearch, exposed kube-apiserver/kubelet, HTTP security-header grades (missing HSTS/CSP/`X-Frame-Options`, permissive CORS, `Set-Cookie` missing Secure/HttpOnly/SameSite), directory-listing/default/debug pages (autoindex, stock nginx/Apache pages, Django/Werkzeug tracebacks, phpinfo), and open admin panels (Grafana anonymous, Jenkins, phpMyAdmin, Kibana answering the GET with app UI vs a 401/login).
**Why it matters:** "Redis with no auth" or "expired cert on a prod port" is discoverable today only by eyeballing banner strings or grepping FTS — there is no category, no severity, and the diff can't say "this host newly became an open exposure." This table is also the shared home for the posture verdicts emitted by features 4, 5, and 7, so weak crypto, TLS hygiene, and pre-auth exposures all land in one severity-scored, diffable place instead of being overloaded into `vulns` (which has no FTS and isn't diffed). Formalizing it makes exposure the *headline* recon output instead of a side effect of banner parsing.
**How it fits lodan:** Add a `findings` table to `store/schema.sql` (`scan_id, ip, port, rule_id, severity, title, evidence`) mirroring `vulns`/`vulns_scan`, with its own FTS index over `title`/`evidence`. Add `enrich/exposure.py` (analogous to `enrich/cve.py`) that reads each service's persisted `ProbeResult.raw` — Redis/Docker/Mongo/ES/k8s flags, `raw['headers']` + cookie attrs from `HTTPProbe`, and body-regex matches extending the `tech_signatures.py` `body_patterns` engine — and emits findings via a new `record_findings()`. Add `new_exposure`/`gone_exposure` to `diff/scanner.py` (`KINDS` + `DiffCounts`) and a `header_grade`/`admin-open` facet to the `query.py` DSL (`_VALID_KEYS`).
**Detection-only:** Pure post-hoc analysis of `ProbeResult.raw` the existing probes already collected (Server header, cookies, and the single allowed GET `/` body/status/favicon) — no additional requests, no login submission, no creds.
